## Improvements after the final review (2026-11-21)

- Bug: ACE editors built inside a hidden tab (fragments, loop, the Instructions'
  code examples) were cropped or empty until something resized them. `init.js`
  now resizes the editors of a tab when it is shown and after a project load.
- Ctrl+Enter / Cmd+Enter runs from anywhere (capture listener on `window`).
- Autosave: the project (with run history) is kept in `localStorage`
  (`cegarplay.project`) and restored at start-up unless `?file=` or `?fresh=1`.
  Loading an example or a file over an edited project asks first (`app.edited`).

  `fragment:L:C` (line within the fragment) and adds `fragment/line/col` to the
  W event; the page marks these lines in the editors after the run (infos in
  blue do not set the red tab marker).
- Run-time errors: a hint sentence for common errors (`relevant/1 derived
  nothing`, glue derives nothing, no progress); the Lua traceback is collapsed.
- Trace panels: atoms flow inline, one line per predicate. When relevant/1
  derives nothing, the runtime first emits a trace step of kind `error` (even
  past the trace cap; the counterexample text only while tracing), and the
  trace view jumps to it.
- New project (Control tab): `Project.starterProject()`, four commented
  fragments that run as they are (downward-closed sets, n = 4 gives 4 solutions).
- The loop script is compiled 500 ms after each edit; errors are marked at once
  (`Editors.setMarks`).
- Run message under the run bar when a run ends in an error or does not
  start (visible from every tab, with a link to the Output tab).
- Output: "Download" next to Solutions saves all solutions (up to 200,000 kept),
  not only the 1,000 shown.
- Fixes after an independent review: two-line clingo locations mapped at both
  ends; a project opened with `?file=` (or a failed restore) does not overwrite
  the kept project until it is edited (`app.saveBlocked`); a stored project that
  fails to load falls back to the example; `Editors.build` clears marks; a run
  cancels the pending live check; trace groups by predicate regardless of sort.

The standalone export, now "Export for clingo", has a run hint below its button.   restart, models, core, clauses, trace); phase 1 tested only the phase 1 subset.
- `rt.stop()` without a message ends with outcome `finished` and `exhausted` =
  whether the last solve without assumptions (or the last search) was exhaustive.

  outcome `stopped`.

## Known problems

- clasp's default enumeration (backtracking, `--enum-mode=bt`) does not keep
  refinement clauses added during `search` in force: later candidates may
  violate them (seen with `tutorial-weak-relevant` in Shape 1: unit clause
  `-pick(4)`, the next candidate has `pick(4)`). The result stays sound (every
  candidate is checked) but refinements prune less, and a too-weak relevant/1
  may lose no solutions in Shape 1. `options "--enum-mode=record"` on the
  abstraction solver keeps them (sum-free n=8: 77 instead of 107 candidates).
  cegar.py behaves the same (rows 1-3 equal its numbers), so the runtime is
  unchanged; the tutorial shows the weak-relevant loss with Shape 2.

## Puzzle generators (2026-11-23)

Three more contrib examples in the `sudoku-unique` pattern (guess a solution and the clues; C
looks for two solutions; clause = a clue that one of them violates). Group `exists-forall`,
`expected: null` (runs stop at the first puzzle). Generator source kept out of the repo; the
contrib JSON files are the source.
- `binairo`: n x n binary puzzle (no three in a row, balanced, distinct rows/columns). 6 x 6 k = 6
  0.8 s; 6 x 6 k = 5 21 s; 8 x 8 k = 12 9 s; 10 x 10 k = 24 6 s (k = 20 > 60 s).
- `futoshiki`: Latin square with values (`givens`) and signs (`signs`, `less/4` atoms in both
  orientations; relevant = signs that fail in a or b). 5 x 5 with 7 signs only 0.8 s (6 signs
  > 120 s); 6 x 6 12 signs 13 s; 7 x 7 18 signs > 120 s.
- `akari` (Light Up): A also designs the black cells (half-turn symmetric, `blacks` of them, or
  `layout/2` from the instance) and chooses `k` numbered ones; the lighting stays private.
  Relevant: every `black/2` atom (the lighting depends on the whole layout) and the numbers that
  fail for a or b. 7 x 7 12 blacks k = 4 0.4 s; 10 x 10 20 blacks k = 8 1.6 s.
- Every counted instance equals a Python brute force (binairo 4 x 4: 72 grids, k = 3/4/5 ->
  0/1152/23040; futoshiki 3 x 3 and 4 x 4: 672, 32, 2944, 13248; akari 4 x 4 / 5 x 5: 0, 12,
  494, 23) and cegarcheck (auto and block). The fixed-layout akari counts (1, 68, 0) agree with
  cegarcheck only (7 x 7 is too big to brute-force).
- `slitherlink`: one loop along grid edges; numbers 0..3 on cells. Rules (both solvers): degree
  0 or 2 at every vertex, reachability from the first used vertex (in a fixed vertex order,
  `later/2` chain, linear), non-empty. A shows `num/3` for k cells, never 4 (a 4 pins the loop
  to one cell's square), and the loop has at least `len` edges (without it the solver picks
  tiny loops that a few zeros pin down). **Bug found on the way:** with the interface at 0..3 but
  A allowed to show a 4, those candidates were rejected by counterexamples that ignored the 4
  (lost solutions; 4 instead of 8 on 2 x 2). The interface must cover every value A can show.
  Timings: 7 x 7 k = 12 len = 28 5.6 s; k = 10 len = 28 > 120 s; k = 10 len = 0 1.7 s;
  10 x 10 k = 30 len = 50 84 s. Counts = brute force over enclosed cell sets (3 x 3: 213 loops,
  516; 4 x 4: 9,349 loops, 128 / 0 / printed 8 / len 12 2,104) = cegarcheck (auto, block).

## Grading by technique (2026-11-23)

`sudoku-graded`: puzzles that need pairs or locked candidates. Fragments `notes` (pencil marks:
choices `out/3`, `known/3`; givens written; written values cross out; `empty/2`; `:- not empty`),
`singles`, `pairs`, `locked`, all as closure constraints and **without the solved grid** (unlike

(sound for any closed marks: the least closed set of such a puzzle lies inside them);
`#heuristic known [1,true]` grows the marks, so clauses are short (the default run's first
counterexample leaves only a 2 x 2 rectangle empty).
