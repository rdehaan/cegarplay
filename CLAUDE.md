# CegarPlay

A static, build-free browser playground for CEGAR loops written in answer set
programming, solved with clingo compiled to WebAssembly.

## Where things are

- Both implementation plans (PLAN.md, PLAN2.md) are done and were removed; they are in
  the git history. `docs/directions/*.md` holds the design behind PLAN2's features; the `spike2/`
  prototypes it cites were removed too (git history).
- `FUTURE-DIRECTIONS.md`: what was considered and not built (language, tools, views, library).
- `PROGRESS.md`: what is done and what is next. **Read it first after any
  context clear. Update it at every checkpoint.**
- `docs/spec-*.md`: specifications. Read only the ones the current phase names.
- `docs/reference-numbers.md`: numbers the implementation must reproduce.
- `spike/`: verified prototype code. Read-only; copy from it.
- `reference/`: clones of logic-game and declarative-cegar. Read-only, git-ignored.
- `guide/`: the design guide (static pages, `chapters.js`, `numbers.json`).
  Its examples are built by `tools/guide.mjs`; `tools/guide-numbers.mjs`
  measures them (`--check` after any change to an example or a page).
- `book/cegarplay.md`: the booklet (guide + tutorial), generated by `tools/export-book.py`.
  Never edit it by hand. Book/web differences go in the HTML as `class="web-only"` (dropped
  from the book) and `class="book-only"` (hidden on the web, kept in the book).

## Rules that are easy to forget

1. An error raised by clingo inside a Lua call kills the WASM instance, even
   inside `pcall`, with no message. Validate ASP text before a run; wrap every
   callback body in its own `xpcall`; never let a Lua error cross a clingo
   frame; check preconditions in Lua before calling clingo.
2. Propagator tables need `init` and all hooks at registration time.
3. After `control:add_clause` returns false, return from `check`.
4. Never read `ctl.statistics` of a control that is solving.
5. Read models from a solve handle only with `h:iter()`.
6. Clause forms: `control:add_clause{ lits }` in `check`; `init:add_clause(lits)` in `init`.
7. No build step, no framework, no request to another origin.
8. `js/compiler.js`, `js/driver.js`, `js/project.js` must not use the DOM or Node APIs.
9. Trust tests over the plan; record deviations in `PROGRESS.md`. Do not change
   reference numbers without finding the cause.
10. An atom that the backend adds to a control before it is grounded must also reach the
    grounder as program text (a choice rule or a fact): clingo 5.8 grounds a rule that projects
    backend-only choice atoms away (`b :- q(X).`) with one instance. See `iface_part` in
    `lua/runtime.lua`.

## Setup (fresh clone, e.g. Claude Code cloud)

Needs Node ≥ 22, Python 3 and git, plus network access to github.com, npm and
PyPI. Run this from the repo root. It also works as a cloud environment's setup script.

```
git clone https://github.com/rdehaan/declarative-cegar reference/declarative-cegar  # required: tests + make-examples read its .lp files
git clone https://github.com/rdehaan/logic-game reference/logic-game                # read-only reference (docs/spec-app.md)
(cd test && npm ci && npx playwright install --with-deps chromium)  # browser tests; add firefox for BROWSER=firefox
(cd spike && npm ci)
pip install clingo                                                  # Python clingo 5.8.x
```

- Without Python clingo, `tools/cegarcheck.py` and `tools/certcheck.py` do not run, and
  the draw and certcheck tests skip.
- One test in `test/project.test.mjs` needs a native `clingo` built with Lua on the PATH.
  It is optional and skips without one.
- `test/serve.py` (the server for the browser tests) uses only the standard library.
- `vendor/` is committed. Run `tools/vendor.mjs` only after an upgrade of clingo-wasm.

## Commands

```
cd spike && npm install && npm test          # sanity check of the environment (9 checks)
cd test && npm install && npm test           # the project's tests (node --test)
node tools/vendor.mjs                        # copy the engine into vendor/
node tools/make-examples.mjs                 # rebuild examples/*.json (+ examples/contrib/*.json)
node tools/make-replays.mjs                  # rebuild examples/replays/*.cprec (after a runtime or example change)
node tools/audit.mjs <id> [--json]           # audit a project (exit 0 sound, 1 unsound)
node tools/make-chat-package.mjs             # dist/chat-package/: docs for writing examples in web chat
node tools/guide-numbers.mjs [--check]       # measure the guide's examples into guide/numbers.json
python3 tools/cegarcheck.py <project.json>   # check a project with Python clingo
python3 tools/export-book.py [--check|--lint] # rebuild book/cegarplay.md (after ANY change to guide/ or tutorial.html)
python3 test/serve.py 8811                   # serve the site; add "coi" for isolation headers
```

## Integrate from cloud session

Use this when the user asks to "integrate from the cloud session" (a Claude Code
cloud session that pushed its work to a branch on origin).

1. `git fetch origin --prune`, then list remote branches newest first:
   `git for-each-ref --sort=-committerdate refs/remotes/origin --format='%(refname:short)  %(committerdate:relative)  %(subject)'`.
   The cloud branch is usually `origin/claude/...`. If there is more than one
   candidate, or none, ask the user which branch (or say nothing has been pushed yet).
2. Present a summary of the changes on that branch relative to `main`: commits
   (`git log main..<branch>`), files changed (`git diff --stat main...<branch>`),
   and a short prose summary of what changed and why, read from the diff. Say
   whether `main` has moved since the branch was made. Don't run the tests unless
   the user asks (the cloud session runs them).
3. Ask the user whether to integrate into `main`, or whether they want changes
   first. If they want changes, make them on a local copy of the branch and summarize again.
4. On approval, integrate with a linear history: fast-forward if possible,
   otherwise rebase the branch onto `main` and then fast-forward. Never create a
   merge commit or squash. On rebase conflicts, stop and ask.
5. Then, without asking again: `git push origin main`, and delete the cloud
   branch on origin (`git push origin --delete <name>`) and any local copy of it.

## Working style

- One phase at a time. Commit at each checkpoint: `Phase N: <title>`.
- Keep output short: pipe long test output through `tail`; never print
  `js/ace.js`, `vendor/clingo-wasm/*.js` or the `.wasm` files.
