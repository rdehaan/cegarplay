How to run experiments headlessly

Goal: run many instances and variants from the command line, on a machine with more cores than a browser tab, and turn the results into a table and a plot.

The example

Any project with a suite; voting-justification has three. Open voting-justification

Steps

  1. One run. node tools/run.mjs voting-justification --instance faith-k1 --solutions all. --instance all runs every instance and compares the expected counts; --variant NAME picks a variant.
  2. A suite. node tools/bench.mjs voting-justification --suite strategies --jobs 4 --out rows.jsonl. One JSON line per cell: outcome, solutions, candidates, refinements, time, the cost, the mean clause length and per-solver calls, time and conflicts. --seconds N overrides the suite's time limit.
  3. Resume and shard. --resume skips the cells already in the file; --shard 0/4 … 3/4 splits a suite over machines.
  4. Report. node tools/report.mjs rows.jsonl --out report writes report.md (per-variant totals with PAR2, the instance × variant matrix, the disagreements), report.csv and a cactus plot report.svg. --metric candidates switches the matrix.
  5. Look in the page. The Campaign tab's Import rows reads the same file.

When to move to native clingo

Export for clingo (Project menu) writes one .lp file with the fragments, the runtime and the loop; clingo file.lp --outf=3 runs it with a clingo built with Lua. Native clingo is several times faster than WebAssembly and has no memory cap; use it for runs of hours, such as ground truth for hard instances.

Pitfalls

  • The engine version is part of a row's key; rows from another version are not reused.
  • With more jobs than cores, times grow; compare candidates, or run with --jobs 1 for timings.
