How-to

How to build an instance set

Goal: instances at several levels of difficulty, with ground truth, so that a loop can be tested and compared.

The example

af-preferred has a hand-written instance, three generated ones and the generator af-gnp (random argumentation frameworks). Open af-preferred

Steps

  1. Move the input out of the program. The problem's data goes into instances (Instances tab), not into shared. Each instance has facts, constants, tags and an expected count or optimum.
  2. Write a generator. A generator is an ASP program with parameters and random draws: @flip(P, K…) (probability P/1000), @int(lo, hi, K…), @perm(N, I, K…), @subset(M, N, I, K…), @weighted((W1, …), K…) and @mallows(N, phi, I, K…). The keys K make draws independent; the seed makes them repeatable.
  3. Preview and add. The generator panel draws instances for a few seeds; add them as recipe instances (stored as generator, parameters and seed, not as facts).
  4. Import files. Import file reads ASP facts, DIMACS graphs, QDIMACS, ASPARTIX, Trivial Graph Format, PrefLib orders and jaggpy scenarios as facts, checked by clingo first.
  5. Get ground truth. Run the reference variant with all solutions, or Export for clingo and run native clingo for longer, or tools/cegarcheck.py (see checking a loop independently). Write the counts into the instances' expected values.
  6. Tag the hard ones (hard, slow) and check everything with Run all, which says how many instances it actually checked.

Pitfalls

  • Random instances of a fixed size are often all easy or all trivial: vary the parameters in a suite grid and look at the scaling plot.
  • An expected count is compared only for a run that was exhausted; Run all now runs such instances to all solutions.
  • js/mine.js searches a generator's grid for hard instances; it is not in the page yet.
