Designing CEGAR loops

A course in building counterexample-guided loops in answer set programming: what goes in the abstraction, how a counterexample becomes a refinement, how a refinement goes wrong, and which loop to choose.

What this guide is

The guide teaches the design of a loop, not the use of the tool. For a tour of the playground's tabs, take the Tutorial; for the loop language and every option, look in the Manual.

You should know answer set programming: choice rules, constraints, #show, and running clingo. You need not know anything about CEGAR.

The loop in one picture

How the links work

Every step of the guide is an example of the playground. A link marked Open loads the example in the playground and shows the program the text talks about. All such links use the same browser tab, so the guide stays where it is. In the playground, press Run; the link "Back to the guide" at the top left brings you back to the paragraph you came from. Loading an example does not replace the project you are editing in the playground until you change it.

The numbers on the pages (candidates, counterexamples, solutions) were measured with the same engine the playground uses, and a test keeps them up to date: your run shows the same numbers.

Chapters

  1. 01Why a loop A problem with one quantifier too many for one program, and the idea of the loop.
  2. 02The first loop: guess, check, block (in preparation) Two programs, two solvers, the glue, and blocking one wrong candidate at a time.
  3. 03Learning from a counterexample (in preparation) relevant/1: a counterexample rules out many candidates at once.
  4. 04Soundness: when a refinement says too much (in preparation) A refinement that excludes a solution, how it shows, and how to test for it.
  5. 05Reading a run (in preparation) The statistics, the trace and the run history, on a larger graph.
  6. 06Getting more out of each check (in preparation) Several counterexamples per candidate, and stronger ones.
  7. 07Designing the abstraction (in preparation) What the abstraction knows in advance, and what it should leave to the check.
  8. 08Loop shapes (in preparation) One search or many solves, and when each pays.
  9. 09Refinements that are rules (in preparation) Grounding a refinement as a program part instead of adding clauses.
  10. 10Checks that look for a witness, and cores (in preparation) When a good candidate is one with an answer set, and refining from a core.
  11. 11Optimisation (in preparation) Bilevel problems: the best candidate that no check can refute.
  12. 12Your own loop: a walkthrough and a checklist (in preparation) A fresh problem from start to finish, and the rules of the guide in one list.
