Playground Tutorial Manual

Glossary

The terms of the guide, each with the chapter that introduces it. The manual's section "Model and terms" is the reference version.

Abstraction
The solver (A) that proposes candidates. It knows part of the problem and learns the rest from refinements. Chapter 1, chapter 7.
Candidate
An answer set of the abstraction: a proposed solution, to be checked. Chapter 2.
Check
The solver (C) that tests a candidate. Usually it looks for a counterexample; a witness check looks for evidence that the candidate is good. Chapter 2, chapter 10.
Counterexample
An answer set of the check under a candidate: proof that the candidate is wrong. Chapter 2.
Interface (glue)
The atoms of the abstraction that the check reads, declared by glue/1 and passed as assumptions. Chapter 2.
Refinement
What the abstraction learns from a counterexample: a clause, a rule, a copy of part of the problem. Chapter 3, chapter 9.
Blocking
The weakest refinement: exclude exactly the refuted candidate. Always sound; the baseline of every chapter. Chapter 2.
relevant/1
The interface atoms a counterexample depends on; G.clause turns them into a clause. Chapter 3.
Sound and complete
A refinement is sound when it removes no solution; a loop is complete when it ends with every solution. Soundness is the property that fails in practice. Chapter 4.
Audit
A test of every refinement against every candidate and counterexample of an instance. Chapter 4; how-to.
Symbolic audit
The audit's question answered by one search for a candidate, a counterexample and a solution its clause removes, instead of a list: also for instances too large to enumerate. Chapter 4.
Instance space
Every instance up to a bound k, written as choice rules over the instance's predicates (a project's spaces). How-to.
Bounded-sound
Sound on every instance of a space up to the bound k ("sound up to k"); it says nothing about larger instances. Chapter 4.
Forced atom
An interface atom that every sound clause for a candidate must contain: some solution differs from the candidate only in that atom. The Refinery names them, with that solution. How-to.
Idealised run
A run in which each step refines one candidate that is still alive with one of the clauses its loop could make. The Refinery computes the shortest and longest such runs and compares a real run with them; Shape 1 runs can be longer, because clasp keeps clauses only weakly. Chapter 5.
Witness check
A check whose answer set means the candidate is good; a failed witness check is refined by its unsat core. Chapter 10.
Core
A subset of the assumptions of a failed solve that is unsatisfiable on its own; a minimal core has no smaller such subset. Chapter 10, chapter 14.
Expansion
A refinement that adds a copy of part of the problem, instantiated with the counterexample. Chapter 9, chapter 13.
Shape
The control structure of a loop: one search with the check inside (Shape 1), solve-check-refine (Shape 2), rules per counterexample (Shape 3), batches (Shape 4). Chapter 8.
Hitting set
A set that meets every set of a family; an abstraction refined by cores computes one. Chapter 14.
Instance
One input of a project: facts and constants, with an expected count or optimum. How-to.
Variant
The same project with other fragments, another loop or other constants; the reference variant is the blocking loop. How-to.
Campaign
A suite of instances × variants × seeds, run cell by cell, read as a matrix and plots. How-to.

Every term is used in the first library example. Open tutorial-first-run
