How-to

How to compare refinement strategies with a campaign

Goal: decide which of several loops (refinements, shapes, options) is better on many instances, and be sure they compute the same thing.

The example

voting-justification has three refinement strategies, three loops built on the third, and the blocking reference as variants, and a suite strategies that runs them all on fifteen questions. Open voting-justification

Steps

  1. Write the variants. Loop tab, Variants: + Add variant. A variant swaps fragments (relevant for relevant_falsified), replaces the loop script, or changes constants. Always keep one variant whose loop is the Reference run (template "Reference run"): it is the ground truth.
  2. Write a suite. The Campaign tab is shown when ticked (Settings, Tabs, Advanced); the Variants section links to it. New suite writes one over all instances and variants; edit its JSON (instances, variants, solver seeds, a time limit per cell).
  3. Run it. Start runs every cell with all solutions, several engines at a time. The rows are kept in the browser: after a reload or an edit, Start runs only the cells whose key changed.
  4. Read the matrix. One row per instance, one column per variant; switch between time, solutions, candidates and refinements (rows and columns in the project's order). The best finished cell of a row is bold (every one of a tie; not for solutions); a cell that did not finish shows its outcome; click a heading to sort by that variant.
  5. Spread over seeds. One run per cell can mislead: a variant may be lucky on one seed. In the bar Solver seeds, set a number of seeds (0, 1, 2, … or random ones, which are written into the suite), tick randomized search (without it every seed searches the same way), and press Set seeds, then Start. The matrix's Seeds picker shows the median, the mean with its standard deviation, a single seed, or the mean followed by every seed: a ranking that holds on every seed is one to trust.
  6. Read the plots. The cactus plot (cells solved against time) compares variants over the whole suite; the scatter plot compares two variants per instance (pick both); a parameter grid adds a scaling plot with a growth factor.
  7. Export. Export matrix (CSV) for a spreadsheet, Export rows for the raw data (JSON lines, the same format as tools/bench.mjs, see running experiments headlessly).

What to look at

  • A cell marked ✗: two finished variants disagree on the solutions or on the optimum. One of them is unsound; hunt it before reading any times.
  • Candidates explain time: a variant that needs fewer candidates but more time has a costly check or a costly refinement. Find where the time goes.
  • On the voting suite, strategy falsified needs far fewer candidates on the four questions that separate the strategies, and the default strategy is no better than blocking: a real finding, and the start of the project kit's first open question.

Pitfalls

  • A time limit that is too short turns every cell into timeout, and the matrix says nothing. Start with a few instances and a generous limit.
  • Times measured with several engines at once are noisier than single runs; compare candidates first, and use solver seeds with randomized search for spread (seeds without it give the same search every time).
  • Only exhausted runs (or finished optimisation runs) are compared for consistency: a cell that stopped at the limit is never marked ✗, but proves nothing either.
