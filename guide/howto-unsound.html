How to hunt an unsound refinement

Goal: a loop finds fewer solutions than it should (or two variants disagree). Find the refinement that removes a solution, and the atom it forgot.

The example

guide-04-one-node marks only one node of a surviving clique as relevant: a refinement that says too much (chapter 4). Open guide-04-one-node

Steps

  1. Confirm. Run the Reference variant (or the template "Reference run") with all solutions. Fewer solutions in your loop means a refinement removed one.
  2. Audit. Press Audit (next to Run). It checks every refinement against every candidate and counterexample of the instance, and names a witness: the candidate, the counterexample, the relevant set, the lost solution and the atoms on which the candidate and the lost solution differ. One of those atoms should have been relevant. On an instance too large to enumerate, audit by symbolic search: the same verdict and the same kind of witness from one search.
  3. See it. Observatory, Candidate space, Compute: one square per candidate, coloured by its fate; lost solutions stand out. The map is of one run, recorded with every step (the line above it names that run). The summary names the first unsound refinement; the box under the map shows the refinement at the cursor (its candidate, counterexample and clause), and a click on a lost solution moves the cursor to the refinement that removed it. The blame matrix shows which atoms each clause relies on. The map shows only the refinements this run made: its search order may avoid the unsound one that the audit found (after a space audit, See it in the candidate space runs the loop on the breaking instance). To see a run that does lose it, Find a run that loses it (on the verdict) or Find a run that loses one (under the map) runs the instance with a randomized search for seeds 1 to 50 until a run loses a solution, keeps that seed, and shows that run's bad refinement.
  4. Understand it. The Refinery (a switch in Settings adds the Refinery tab) computes the same candidates and counterexamples and keeps them. Its step inspector, on the audit's witness (Inspect this candidate), lists every clause the loop could make for that candidate, marks the unsound ones with the solution they lose, draws the smallest sound clause, and names the forced atoms: every sound clause must contain them, because some solution differs from the candidate only there. The forced atoms missing from the loop's clause are the ones to mark relevant.
  5. Shrink it. If the instance is large, Fuzz (Instances tab) audits instances from small to large, stops at the first unsound one and shrinks it (instances marked "no audit" get the symbolic audit). With a space (Audit by space) the search for the smallest breaking instance is exhaustive: k = 1, 2, … until one breaks.
  6. Keep it. Fuzz's card, and the witness of a space audit, save the small instance as a regression instance; Run all instances checks it from then on.
  7. Fix and re-audit. Mark the atom relevant (or fix the refine part), audit again.

Pitfalls

  • The audit is per instance: "sound" means sound on this instance. Audit several, small ones first, check a space up to a bound, and use certificates (Loop tab) for a guarantee that does not depend on the instance. "Sound up to k" covers the space below k only.
  • Too many solutions is a bug too: a core taken from the wrong check (chapter 10) accepts wrong candidates.
  • Blocks and cores need no audit; the audit refuses loops refined only by them.
