Chapter 12

Your own loop: a walkthrough and a checklist

This last chapter builds a loop for a problem the guide has not used, from the plain statement to a measured, tested loop, naming at each step the chapter it applies. Then it collects the rules of all chapters into one checklist.

The problem, and its quantifiers

A robot stands somewhere in a 3 × 3 room, and does not know where. It can move east, west, north or south; a move against a wall leaves it where it is. Find a plan of t moves that brings it to the centre cell from every start cell. There are no observations along the way: the same moves are made whatever the start.

State the quantifiers first (chapter 1): there is a plan such that for all start cells the robot ends in the goal. The plan is the guess; a start cell from which the plan fails is a counterexample. The library example conformant-planning is the same problem in a larger room; we start small, as chapter 4 advises.

Step 1: the abstraction, with an empty check

The room, the moves and the horizon go into shared. The abstraction guesses one move per step:

1 { do(T,D) : dir(D,_,_) } 1 :- step(T).
#show do/2.

From the fragment abstraction of guide-12-step1-guess.

Before writing the check, run the abstraction with a check that is just #false.: it accepts everything, and the count of solutions is the size of the candidate space (chapter 1). For t = 6 that is 4,096 plans, four moves at each of six steps. Small enough for a blocking loop. Open step 1

Step 2: the check, the glue, the ground truth

The check guesses a start cell, follows the plan from it, and demands that it ends off the goal (chapter 2: an answer set means the candidate is wrong):

1 { start(X,Y) : free(X,Y) } 1.
at(X,Y,0) :- start(X,Y).
at(X2,Y2,T) :- at(X,Y,T-1), do(T,D), to(X,Y,D,X2,Y2).
:- goal(X,Y), at(X,Y,t).
#show start/2.

From the fragment check of guide-12-step2-block.

It reads do/2, so the glue shares exactly that:

glue(do(T,D)) :- step(T), dir(D,_,_).

Run it with the Reference run template, which blocks each failing plan (chapter 2). This run is the ground truth for everything that follows: 80 plans work, found among 4,096 candidates. Open step 2

Step 3: a first relevant/1, tested and measured

Which interface atoms does a failing start cell depend on (chapter 3)? The robot's path from that cell goes through every step, and changing any single move can send it elsewhere, possibly to the goal. So every move of the plan is relevant:

relevant(do(T,D)) :- do(T,D).

The soundness test (chapter 4) passes: 80 solutions, as in step 2. The measurement (chapter 5) shows the catch: 4,096 candidates, no better than blocking. Marking every move is a block in fewer literals (chapter 3). The counterexample's lesson is not "one of these moves must change". Open step 3

Step 4: decide clause or rule, and pick the shape

What a failing start cell really teaches is: "the plan must also work from here". That is not a statement about a few moves, but a copy of the robot that starts in that cell and must reach the goal: a rule refinement (chapter 9).

#program refine(k).
% cex(k,start(X,Y)): the k-th counterexample is a start cell. Follow the plan from there ...
at(k,X,Y,0) :- cex(k,start(X,Y)).
at(k,X2,Y2,T) :- at(k,X,Y,T-1), do(T,D), to(X,Y,D,X2,Y2).
% ... it has to end in the goal.
:- goal(X,Y), not at(k,X,Y,t).

From the fragment refine of guide-12-step4-rules (the constant here is t, so the part may use k).

Rule refinements need a solver that is not searching, so the shape is Shape 3: solve, check, expand, solve again (chapter 8). Every head contains the parameter (chapter 9). The result: 83 candidates and only 3 counterexamples; once the plan works from three well-chosen start cells, it works from everywhere. The soundness test passes again: 80 solutions. Open step 4

Step 5: scale the constants

Only now scale (chapter 5). With t = 7 the rule loop finds 560 plans from 562 candidates. The library example conformant-planning is the same loop in a 4 × 4 room with a pillar and t = 8: 3 plans after 11 candidates, where a blocking run has to wade through tens of thousands. Open conformant-planning

The order of the steps is the point: the empty check before the real one, the blocking loop before any refinement, the soundness test before any measurement, and the small instance before the large one.

The checklist

Every rule from the recaps of chapters 1 to 11, grouped by what it is about.

The problem

  • Look for the quantifiers. "There is an X such that for all Y …" is the shape a loop is for. Chapter 01
  • A guessed atom means "there is one". One program cannot say "for all" with it. Chapter 01
  • Split the problem into a guess (the abstraction) and a test of one guess (the check); each is an ordinary program. Chapter 01

The abstraction

  • The abstraction over-approximates: every solution must be a candidate. Chapter 02
  • Put into the abstraction what is cheap to state and true of every solution; leave to the loop what is too much to list. Chapter 07
  • Glue what the check depends on, which may be a derived atom; one refinement then covers every candidate with the same value. Chapter 07
  • Atoms the check need not see stay out of the glue; count solutions on the interface atoms. Chapter 07
  • Nothing in the abstraction may cut a solution. Symmetry breaking is for existence, not for lists. Chapter 07
  • To optimise, ask the abstraction for the best candidate first; the first one that survives the check is optimal. Chapter 11

The check

  • The check has an answer set exactly when the candidate is wrong; that answer set is the counterexample. Chapter 02
  • Glue every atom of the abstraction that the check reads. An atom that is not glued is silently false in the check. Chapter 02
  • Know your check's polarity: does an answer set mean wrong (counterexample) or good (witness)? Chapter 10
  • Several counterexamples per candidate save candidates and cost check work; measure the trade. Chapter 06
  • A counterexample that depends on few atoms gives a short, strong clause. Ask for it with #minimize and optimal when checks are cheap. Chapter 06

The refinement

  • Mark with relevant/1 the interface atoms the counterexample depends on, and no others. The refinement then rules out every candidate that agrees on them. Chapter 03
  • For every refinement, argue that every solution satisfies it. If the relevant atoms keep their values, the counterexample must still be one. Chapter 03
  • Marking every interface atom is blocking: safe, and no faster. Chapter 03
  • A counterexample can depend on an atom being false. Mark it too. Chapter 04
  • A refinement must exclude the candidate it was made from, and every solution must satisfy it. Chapter 09
  • Write the clauses in the check with clause/3 when relevant/1 cannot say what you need. Chapter 06
  • Use a rule refinement when the lesson is not "one of these atoms must change": sums, comparisons, copies of the problem. Chapter 09
  • Every head of a refine part contains its parameter, and no constant has the parameter's name. Chapter 09
  • Refine from the core only when an unsatisfiable check means the candidate is wrong. Chapter 10
  • Cores are not minimal; shrink them when clause length matters. Chapter 10
  • When the inner problem optimises, refinements carry numbers; write them as rules. Chapter 11

Soundness

  • Blocking is always sound and always slow. Keep the blocking loop as the ground truth for small instances. Chapter 02
  • A refinement that is too strong removes solutions without any sign. The run still finishes, exhausted. Chapter 04
  • Test soundness by comparison: the blocking loop and your loop, same fragments and constants, all solutions, both exhausted, same count. Chapter 04
  • Press Audit on a small instance: it checks every refinement against every solution, and its witness names the atom that should have been relevant. Chapter 04
  • Run the test on several small instances: a wrong loop can be right on one. Chapter 04
  • Test soundness where the blocking loop finishes; scale only afterwards. Chapter 05
  • An optimum is only as good as the soundness of every refinement; test the bounded version first. Chapter 11

Measuring

  • Read the first steps of the trace: candidate, counterexample, refinement. Mistakes in a refinement show there first. Chapter 05
  • A good run has short clauses, few candidates beyond the solutions, and no solver that dominates without reason. Chapter 05
  • Solver options can change the number of candidates, never the solutions of a sound loop. Chapter 05
  • Rule refinements grow the abstraction; watch its size and grounding time. Chapter 09
  • Compare shapes by the run history: same fragments, only the loop changes, the counts must agree. Chapter 08

The loop shape

  • Start with Shape 1: one search, clauses on the fly. It is the fastest when checks are cheap. Chapter 08
  • Use Shape 2 when checks are expensive or refinements are rules; block every accepted solution yourself. Chapter 08

Exercise 1

Step 3 claimed that changing a single move can send the robot elsewhere. Take a plan that fails from some start cell and try to find a single move whose change makes it succeed from that cell. Why does that make every move relevant?

Solution

Any plan that ends in the goal from that cell differs from the failing one in some moves. If a move were not marked, the clause would also rule out plans that differ from the candidate only in that move, and one of them might work from every cell: a lost solution (chapter 4). The moves the robot "wastes" against a wall look irrelevant, but changing one of them changes where it is for the rest of the plan. Open step 3

Recap

  • Quantifiers, abstraction with an empty check, real check and glue, blocking run, first refinement, soundness test, measurement, clause or rule, shape, and only then larger constants.
  • Before you trust a loop, go through the checklist.
