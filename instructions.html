What CEGAR is

CEGAR (counterexample-guided abstraction refinement) splits a hard problem into a solver that proposes candidates and a solver that checks them. When the check finds a counterexample, the loop adds a refinement to the first solver that rules out the candidate, and usually many similar ones. The loop ends when the first solver has no candidates left; every candidate that passed the check is a solution.

CegarPlay runs such loops in your browser. The problem is written in answer set programming, the loop is a short script, and both run in clingo compiled to WebAssembly. The examples come from declarative-cegar.

Four concepts

  • Fragments are named pieces of ASP text, edited in the Programs tab. The default names are shared, abstraction, glue and check, but you can add, rename and reorder them.
  • Solvers are clingo instances, declared in the loop script. Each solver grounds a list of fragments, for example solver A = shared + abstraction, and may get clingo options.
  • Links connect two solvers. A link G = A -> C via shared + glue computes the interface atoms (the atoms both solvers talk about) from the glue fragments. G(M) turns a candidate M of A into assumptions for C.
  • Refinements are what the loop adds to a solver after a counterexample: a clause over interface atoms (G.clause, G.block, G.core, G.clauses), or new rules grounded from a #program part (expand).

ASP conventions

  • glue/1: in the glue fragments of a link, every derived atom glue(T) makes T an interface atom. The link fixes the values of these atoms in the target solver from the candidate. If no glue/1 atom is derived, the run stops with an error naming the link. (Old files that show interface atoms directly can be read with the link option legacy.)
  • relevant/1: in the check, relevant(T) marks the interface atoms a counterexample depends on. G.clause(M, X) builds the clause "at least one relevant atom must change". If relevant/1 derives nothing, the run stops with relevant/1 derived nothing for link G. Rules that are too weak make the clause too strong: it then removes candidates that are solutions.
  • #program part(k).: a part that S.expand(part, name = ...) grounds once per call, with k set to 1, 2, 3, ... and the facts name(k, T) added first. Put k in every head of the part. Otherwise each expansion adds the same atoms again, the candidate comes back unchanged, and the no-progress guard stops the run.
  • clause/3: a check can state its refinements itself with atoms clause(Id, T, true) or clause(Id, T, false). Each Id gives one clause; true adds the literal T, false adds not T. T must be an interface atom of the link. Use them with reject M with G.clauses(X).

A clause/3 rule for the graph colouring check could look like this:

% one clause: one of the missing edges must be added clause(1, edge(N,M), true) :- node(N), node(M), N < M, not edge(N,M).

Walk-through: graph colouring

The default example looks for connected graphs on n nodes with a colouring of the leaves (nodes with one neighbour) that no proper 3-colouring of the whole graph extends. Guessing a graph is easy; checking that no colouring exists is the hard part, so it goes to a second solver.

  • shared declares #const n=10. and node(1..n). It is added to every solver. The Constants table in the Loop tab sets n = 6, which overrides the value in the text.
  • abstraction guesses the edges, requires the graph to be connected, finds the leaves and guesses leaf_color/2, with two mild restrictions. Its last part, #program refine(k)., is used only by Shapes 3 and 4.
  • glue makes edge/2, leaf/1, color/1 and leaf_color/2 interface atoms.
  • check looks for a proper 3-colouring that agrees with the leaf colouring. If it finds one, that is a counterexample. Its relevant/1 rules say what would break it: a missing edge, or a different leaf colour.

The check's relevant/1 rules:

relevant(edge(N,M)) :- node(N), node(M), N < M, not edge(N,M). relevant(leaf_color(N,C)) :- leaf_color(N,C), leaf(N). relevant(leaf_color(N,C)) :- node(N), not leaf(N), color(C), not color(N,C).

The last rule is an addition to the original example: a node that is not a leaf now may become one later. Without it the clauses are too strong. The example "graph colouring (original rules)" leaves it out and finds only 9,270 solutions instead of 10,698.

The loop is Shape 1: A searches, and for every candidate C looks for a counterexample; if there is one, the candidate is rejected with a clause. With Solutions set to all, press Run. After a few seconds the live line shows 31,776 candidates, 21,078 counterexamples, 21,078 refinements and 10,698 solutions.

  • Output lists the solutions (edges, leaves and leaf colours), clingo's messages, and the trace. The trace shows the first steps one at a time: the candidate, the counterexample, and the refinement. Candidate atoms that occur in the refinement are highlighted.
  • Statistics shows the counts, a table per solver, the clause lengths and the charts. See Reading the statistics.

The loop language

A loop script is indented like Python: 4 spaces per level, no tabs. # starts a comment. Declarations come first, then statements. Truth follows Lua: only false and none are false.

Declarations

ScriptMeaning
solver A = shared + abstraction options "--heuristic=Domain"A clingo instance that grounds these fragments, with these options (split on spaces).
link G = A -> C via shared + glueA link from A to C; the interface atoms come from glue/1 in these fragments. Add legacy for unwrapped glue atoms, compat to make relevant(T) a free choice as in the Python prototype.

Statements

ScriptMeaning
x = eAssign a variable. Variables are local to the main script or to one on candidate block.
if a: ... elif b: ... else: ...Conditional.
loop:Repeat forever; leave with break or stop.
while e:Repeat while e is true.
repeat: ... until eRun the block, then stop once e is true.
for x in e:Run the block for each element of the list e.
breakLeave the innermost loop.
continueGo to the next round of the innermost loop.
search A: / on candidate M: / blockRun A's own search; call the block for every candidate M. A candidate that is not rejected is a solution.
reject M with eAdd the clause (or list of clauses) e to the searching solver. Only inside on candidate.
accept MCount M as a solution (for models from solve; inside a search, not rejecting already accepts).
restartEnd the current search early; the next search starts afresh. Solutions found so far are not reported again.
stop "msg"End the run with outcome stopped.
count n by eAdd e (default 1) to the custom counter n.
log a, bPrint a line to the messages in the Output tab.

A block may also follow the colon on the same line, if it is a single simple statement: if not M: stop.

The compiler checks the script before every run: unknown fragments, solvers or links, reject outside on candidate, S.add or S.expand inside the search of S, nested searches, and indentation. The Lua it produces is shown in the Internals tab (?internals=true).

The five templates

Pick a template in the Loop tab and press Insert. All five use the same declarations.

Shape 1: check inside the search

The check runs inside A's search; a counterexample rejects the candidate at once. Usually the fastest.

solver A = shared + abstraction solver C = shared + check options "--heuristic=Domain" link G = A -> C via shared + glue search A: on candidate M: X = C.solve(assume G(M)) if X: reject M with G.clause(M, X)

Shape 2: solve, check, refine, solve again

The classic loop: each round solves A from the start, with the new clauses added.

solver A = shared + abstraction solver C = shared + check options "--heuristic=Domain" link G = A -> C via shared + glue loop: M = A.solve() if not M: stop X = C.solve(assume G(M)) if X: A.add(G.clause(M, X)) else: accept M A.add(G.block(M))

Shape 3: ground rules per counterexample

As Shape 2, but each counterexample is passed to the refine(k) part, which grounds new rules.

solver A = shared + abstraction solver C = shared + check options "--heuristic=Domain" link G = A -> C via shared + glue loop: M = A.solve() if not M: stop X = C.solve(assume G(M)) if X: A.expand(refine, cex = X.atoms(color/2)) else: accept M A.add(G.block(M))

Shape 4: search, collect, ground in batches

Searches, blocks each failed candidate, collects 20 counterexamples, restarts, and grounds them all at once.

solver A = shared + abstraction solver C = shared + check options "--heuristic=Domain" link G = A -> C via shared + glue pending = [] repeat: search A: on candidate M: X = C.solve(assume G(M)) if X: pending.push(X) reject M with G.block(M) if pending.size >= 20: restart grounded = pending.size for X in pending: A.expand(refine, cex = X.atoms(color/2)) pending.clear() until A.exhausted and grounded == 0

Reference run (block only)

Shape 1 that rejects exactly one candidate at a time. Slow, but always sound.

solver A = shared + abstraction solver C = shared + check options "--heuristic=Domain" link G = A -> C via shared + glue search A: on candidate M: X = C.solve(assume G(M)) if X: reject M with G.block(M)

Refinement variants

Each line replaces the check and refinement inside a template.

VariantScript
Several counterexamples per candidatefor X in C.models(assume G(M), limit 5): reject M with G.clause(M, X)
Smallest refinement (add #minimize { 1,T : relevant(T) }. to the check)X = C.solve(assume G(M), optimal)
Refine from an unsat core, for checks that look for a witnessif not C.solve(assume G(M)): reject M with G.core(C)
Two-stage checkX = C1.solve(assume G1(M)), then if not X: X = C2.solve(assume G2(M))
Refinement computed by its own solverY = R.solve(assume GA(M), GC(X)), then reject M with GA.clause(M, Y)
Explicit clauses from ASPreject M with G.clauses(X)

Rejecting the same candidate several times is allowed: the first clause is added at once, the others just before the solver checks its next candidate.

Reading the statistics

  • Candidates: candidates seen by an on candidate block, plus models returned by solve of a solver with no incoming link.
  • Counterexamples: satisfiable solves that were given assumptions, so usually the checks that failed.
  • Refinements = clauses + expansions. In Shape 1 every counterexample gives one clause, so the two numbers agree.
  • Solutions: candidates accepted. "exhausted" after the outcome means the search ran to the end, so the count is complete.

The solver table has one row per solver:

ColumnMeaning
Fragments, OptionsAs declared in the loop script.
Calls, Sat, UnsatNumber of solves and how they ended. For the check, Sat = counterexamples found.
Solving, Per callTime spent solving, and its mean per call. Time in a check called from a search counts for the check only.
GroundingTime spent grounding, including expansions.
Choices, Conflicts, Restartsclasp's counters, read when the solver is idle. A dash means not yet known.
Atoms, RulesSize of the ground program.
ExpansionsNumber of expand calls on this solver.

The Refinements table gives the number of clauses, their mean and largest length, expansions, restarts, and automatic blocks (clauses that keep accepted solutions from coming back after a restart). Short clauses are strong refinements: each removes many candidates.

The charts show candidates and refinements over time, where the time went (solving per solver, grounding, the rest), and the clause lengths in 8 buckets (1, 2, 3–4, 5–8, 9–16, 17–32, 33–64, 65+).

The run history keeps one row per finished run in this session, with the loop, outcome, time, counts and seed. "Rerun with 5 seeds" adds five rows. A row marked ⚠ means: another run of the same fragments with all solutions also finished exhausted, but found a different number of solutions. At least one of the two loops is not sound.

The reference run as a soundness check

A clause from G.clause removes every candidate that agrees with the counterexample on the relevant atoms. If the relevant/1 rules miss an atom, the clause also removes real solutions, and nothing warns you. G.block removes only the candidate itself, so the reference run is always sound.

To test your rules on a small instance: set Solutions to all, run your loop, then insert the Reference run template and run again. Both counts appear in the run history; if they differ, the rows get the ⚠ marker. For graph colouring at n = 6 the reference run finds 10,698 solutions (about 10 s); the example with the original rules finds 9,270 with Shape 1, so its rules are too weak.

Limits and gotchas

  • The time limit and the candidate limit (Loop tab, 0 = none) end a run with outcome limit. The default time limit is 60 s.
  • The trace records only the first steps (Trace steps, default 200; 0 turns it off). A note says when the cap was reached.
  • The seed matters only together with randomising options, such as options "--rand-freq=0.05". Without them, every seed gives the same search.
  • The no-progress guard stops Shapes 2 and 3 with the refinement made no progress when a refinement does not change the next candidate. Check that every head in a #program part(k). contains k.
  • An error inside clingo itself (not in the loop script) ends the run with "clingo stopped unexpectedly" and no message. The Output tab then shows the last lines clingo printed.
  • Validation runs before every run: the fragments are parsed and the loop script is compiled. Problems are marked in the editors, and the run does not start while there are errors.
  • Abort always works. Pause, Step, Stop and threads (clingo-mt) need a cross-origin isolated page; otherwise these controls are hidden or disabled.
  • All editors are read-only while a run is active.
  • The loop script is compiled while you type; errors are marked after a short pause, before you press Run.
  • New project (Control tab) starts from four small fragments that run as they are: replace them with your own problem.
  • Ctrl+Enter (Cmd+Enter on a Mac) runs the project from anywhere on the page, also from inside an editor.
  • clingo's warnings and infos (for example "atom does not occur in any rule head") name the fragment and the line, and after the run they are marked in the editor: blue for an info, yellow for a warning.
  • The project you are editing is kept in this browser and comes back after a reload. Loading an example or a file asks first if you changed the project. To keep a project, download it; ?fresh=1 starts from the default example.
