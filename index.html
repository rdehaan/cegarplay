CegarPlay runs CEGAR loops (counterexample-guided abstraction refinement) written in answer set programming, with clingo running in your browser. Pick an example below, or start one from Project. A project is written in the Write tabs; press Run (or Audit) and read the run in the Results tabs. New here? Take the guided tour (five minutes), or start with the Tutorial. More tabs (the Observatory, the Campaign tab and the Refinery) can be switched on in Settings.

Programs ?

The ASP fragments of the project. A solver is built from fragments (see the Loop tab). Problems found before a run are marked in the editors. Tutorial: Fragments, solvers and links. Manual: ASP conventions.

The rules of the project's domain views are edited with their view in the Observatory tab: a view only draws the steps of a run and is not part of the loop.

Loop ?

The loop script declares the solvers and the links between them and says how they call each other; below it are the constants and the settings of a run. Tutorial: Writing loop scripts · Choosing a loop shape. Manual: The loop language · Settings.

Variants

The same project with other fragments swapped in, its own loop script or other constants. The run bar's Variant picker chooses the variant of a run (also for Audit and Run all instances); a campaign suite compares variants on the same instances.

Instances ?

An instance is a set of facts and constant values that a run applies on top of the project: the problem's input, kept apart from its encoding. The run bar picks the instance a run uses; Run all instances runs each one and compares its count with the expected one; Fuzz looks for an instance on which the loop is unsound. Tutorial: One project, many instances. Manual: Instances · Generators · Fuzz.

Campaign ?

A suite is a grid of instances × variants × solver seeds; each cell is one run with all solutions. Rows are kept in this browser: Start again resumes and skips the cells already run. Exhausted variants that disagree on an instance are marked red; tools/bench.mjs runs the same suite headless. The run bar's Instance and Variant do not apply here: a suite names its own instances and variants. Tutorial: Campaigns. Manual: Campaigns.

Output ?

The last run or audit: its result, the solutions, the trace one step at a time, and the messages. Tutorial: Reading the trace and the statistics · The audit. Manual: Output tab · Audit.

    Refinery ?

    What a loop could have done, not just what it did: at one step, every refinement clause that was possible there; over a whole run, how its length compares with the shortest and longest runs the same refinements allow. Computed on small instances, from every candidate and counterexample, by the Refinery's own engine (runs and audits go on as usual). Manual: Refinery tab · Audit · Candidate space.

          The shared fragment
          
        
          Rules that every solver needs: domains, constants, common definitions. In the default
          loop it is part of the abstraction solver, the check solver and the glue.
          
        
          The problem's input (a graph, a formula, an election) belongs in an instance (Instances
          tab): its facts reach every solver and the glue, ahead of all fragments, so one encoding
          serves many inputs.
          
      
          
    
          
  
          
  
          
    
          
      
          
      
          
        
          The abstraction fragment
          
        
          Proposes candidates. It over-approximates the solutions: every solution is a candidate,
          but a candidate may be refuted by the check. Refinements make it more precise.
          
        
          For rule refinements it may contain a part #program refine(k).; the loop
          grounds it once per counterexample with facts such as cex(k, T). Every head
          in that part must mention k, or the second refinement has no effect.
          
      
          
    
          
  
          
  
          
    
          
      
          
      
          
        
          The glue fragment
          
        
          Says which atoms the abstraction and the check share. Every atom glue(T) it
          derives makes T an interface atom: its value in a candidate is passed to the
          check as an assumption.
          
        
          Files written for the old prototype list the atoms without glue(...); the
          link then needs the keyword legacy.
          
      
          
    
          
  
          
  
          
    
          
      
          
      
          
        
          The check fragment
          
        
          Looks for a counterexample to the candidate, given the values of the interface atoms.
          If it finds one, it marks with relevant(T) the interface atoms the
          counterexample depends on. The refinement then says: one of these atoms must change.
          
        
          If relevant/1 marks too few atoms, the refinement also removes good
          candidates. Press Audit to find out: it checks every refinement against every
          solution of a small instance and names the atom that should have been relevant.
          
      
          
    
          
  
          
  
          
    
          
      
          
      
          
        
          The loop script
          
        
          Declares the solvers (solver A = shared + abstraction), the links between
          them (link G = A -> C via shared + glue) and how they call each other.
          Start from a template; the Tutorial tab explains the language (lesson 10), and the
          manual has the full reference.
