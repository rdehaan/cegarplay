1. What CEGAR is

CEGAR (counterexample-guided abstraction refinement) splits a hard problem into a solver that proposes candidates and a solver that checks them. When the check finds a counterexample, the loop adds a refinement to the first solver that rules out the candidate, and usually many similar ones. The loop ends when the first solver has no candidates left; every candidate that passed the check is a solution.

CegarPlay runs such loops in your browser. The problem is written in answer set programming, the loop is a short script, and both run in clingo compiled to WebAssembly. The larger examples come from declarative-cegar.

2. Your first run

A set of numbers is sum-free if no two members (possibly the same one twice) add up to a third member. The first example lists all sum-free subsets of 1..8. Solver A guesses any set; solver C looks for a sum inside it.

Run it. It takes a fraction of a second, and the run bar shows 107 candidates, 46 counterexamples, 46 refinements, 61 solutions. Then open the Output tab:

  • Solutions lists the 61 sets (the first one is the empty set).
  • Trace shows the run one step at a time. Step 1: the candidate is pick(2) pick(4); the check finds the counterexample sum(2,2), because 2 + 2 = 4; the refinement is the clause -pick(2) ∨ -pick(4): from now on, 2 and 4 are never picked together.

One clause rules out every set that contains both 2 and 4, not only this candidate. That is why 46 refinements are enough for a search over 256 sets. (Step 2 may show a candidate that the clause of step 1 already rules out. In this loop shape clasp does not always apply a fresh clause to the very next candidate; the check catches it again, and the result is the same.)

3. Fragments, solvers and links

Open the Programs tab. The problem is split into four fragments, named pieces of ASP text:

  • shared: num(1..n). Every solver needs it. n is set in the Constants table of the Loop tab (here n = 8), which overrides a #const in the text.
  • abstraction: { pick(X) : num(X) }. The candidates: any set.
  • glue: glue(pick(X)) :- num(X). Each derived glue(T) makes T an interface atom: an atom both solvers talk about. When the check runs, these atoms are fixed to their values in the candidate.
  • check: has an answer set exactly when the candidate is wrong, and marks with relevant(T) the interface atoms the counterexample depends on:
1 { sum(X,Y) : num(X), num(Y), X <= Y, X + Y <= n } 1. :- sum(X,Y), not pick(X). :- sum(X,Y), not pick(Y). :- sum(X,Y), not pick(X+Y). relevant(pick(X)) :- sum(X,Y). relevant(pick(Y)) :- sum(X,Y). relevant(pick(X+Y)) :- sum(X,Y).

Now open the Loop tab. The loop script first declares the solvers (clingo instances, each grounding a list of fragments) and a link between them:

solver A = shared + abstraction solver C = shared + check link G = A -> C via shared + glue search A: on candidate M: X = C.solve(assume G(M)) if X: reject M with G.clause(M, X)
  • search A: runs A's search and calls the on candidate block for each candidate M.
  • G(M) turns the candidate into assumptions for C: the values of the interface atoms in M.
  • C.solve(...) returns a counterexample, or none if the check is unsatisfiable.
  • G.clause(M, X) is the refinement: at least one atom marked relevant in X must change its value. A candidate that is not rejected is a solution.

The same structure, at a larger scale: the default example looks for connected graphs on n nodes with a colouring of the leaves that no proper 3-colouring of the whole graph extends. Guessing a graph is easy; checking that no colouring exists is the hard part, so it goes to the check solver, and a counterexample is a colouring. Its fragments have comments; read them in the Programs tab.

With Solutions set to all, a run takes a few seconds: 31,776 candidates, 21,078 counterexamples and refinements, 10,698 solutions.

4. Reading the trace and the statistics

The trace (Output tab) records the first steps of a run (Trace steps in the Loop tab, default 200). Each step shows the candidate, the counterexample and the refinement; candidate atoms that occur in the refinement are highlighted. If a run stops with an error about a candidate, the trace jumps to that step.

The Statistics tab, after a run:

  • Candidates, Counterexamples, Refinements (clauses + expansions), Solutions. "exhausted" after the outcome means the search ran to the end, so the count of solutions is complete.
  • A table per solver: solve calls and how they ended, time spent solving and grounding, clasp's counters. For a check, Sat is the number of counterexamples found.
  • The Refinements table: number of clauses and their lengths. Short clauses are strong refinements: each removes many candidates.
  • Charts of candidates and refinements over time, where the time went, and the clause lengths.
  • The run history: one row per finished run in this session. Use it to compare loops on the same problem.

5. When relevant/1 is too weak

A clause from G.clause removes every candidate that agrees with the counterexample on the relevant atoms. If the relevant/1 rules miss an atom, the clause also removes real solutions, and nothing warns you. This example marks only the sum X + Y, not X and Y:

% Too weak: X and Y are not marked. relevant(pick(X+Y)) :- sum(X,Y).

Run it: 11 solutions instead of 61. After the counterexample sum(2,2), the refinement says "never pick 4", also for sets without 2.

How to find out: G.block(M) removes only the candidate itself, so a loop that refines with G.block is always sound. In the Loop tab, choose the template Reference run, press Insert, and run again: 61 solutions (and 256 candidates, one per set). Both runs are in the run history of the Statistics tab, and since both ran to the end with different counts, they are marked ⚠.

Do this check on a small instance of every new problem: run your loop with Solutions all, then the Reference run, and compare. (This example uses Shape 2, explained in the next lesson. With Shape 1 the loss may not show at this size, for the reason mentioned in lesson 2.)

The same story at a larger scale: the original rules of the graph colouring example lack the third relevant/1 rule (a node that is not a leaf may become one later) and find 9,270 solutions instead of 10,698.

6. Choosing a loop shape

The Loop tab has five templates. They use the same declarations and differ in how the solvers call each other. The examples below are graph colouring at n = 5; all five find the same 101 solutions.

ExampleCandidatesCounterexamplesRefinements
Shape 11,4211,3201,320 clauses
Shape 21,2591,1581,259 clauses (1,158 + 101 blocks)
Shape 3222121121 expansions + 101 blocks
Shape 4327226226 blocks + 226 expansions
Reference run3,3733,2723,272 blocks

Shape 1: check inside the search

One search of A for the whole run; the check runs inside it, and a counterexample rejects the candidate at once with a clause. Usually the fastest. Use it first.

Shape 2: solve, check, refine, solve again

The classic loop: each round solves A from the start, with the new clauses added. A solution must be blocked by hand (A.add(G.block(M))), or the next round finds it again. Easier to follow and to change than Shape 1; slower, because every round is a new solve call.

loop: M = A.solve() if not M: stop X = C.solve(assume G(M)) if X: A.add(G.clause(M, X)) else: accept M A.add(G.block(M))

Shape 3: ground new rules per counterexample

Instead of a clause, each counterexample is handed to the part #program refine(k). of the abstraction, which grounds new rules: A.expand(refine, cex = X.atoms(color/2)) adds the facts cex(k, T) and grounds refine(k). Rules can say more than one clause: here, that the next graph must break the colouring found (an edge between two nodes of the same colour, or a different leaf colour). Few candidates, but grounding costs time. Look at the end of the abstraction fragment.

Shape 4: search, collect, ground in batches

As Shape 3, but the search goes on: each failed candidate is blocked and its counterexample kept; after 20, the search restarts and grounds them all at once. Fewer, larger grounding steps.

Reference run

Shape 1 with G.block(M): rejects exactly one candidate at a time. Slow, but always sound: its count is the truth to compare with (lesson 5).

7. Writing loop scripts

A loop script is indented like Python: 4 spaces per level, no tabs; # starts a comment. Declarations (solver, link) come first, then statements. The examples in this lesson are small (most are sum-free sets again); each shows one feature, with comments in the Loop tab. The quick reference below lists everything.

The basics

Shape 2 written out with most statements: variables, loop, if/elif/else, break, stop "message", accept, lists ([], push, size), for, count and log. After a run, the log lines are under Messages in the Output tab, and the counters (refinements, largest) in the Statistics tab.

X = C.solve(assume G(M)) # look for a counterexample to M if X: count refinements # a counter, shown in the Statistics tab A.add(G.clause(M, X)) # one relevant atom must change elif found >= 1000: stop "enough solutions" # ends the whole run, with a message else: accept M # M is a solution

Several counterexamples per candidate

C.models(..., limit 3) returns a list of up to three counterexamples; each one refines A. The same 61 solutions with 100 candidates instead of 107.

for X in C.models(assume G(M), limit 3): reject M with G.clause(M, X)

The smallest refinement

With optimal, C.solve returns an optimal model of a #minimize statement. The check gets #minimize { 1,T : relevant(T) }., so it prefers counterexamples that mark few atoms, which give shorter clauses.

X = C.solve(assume G(M), optimal)

Two checks

Sum-free sets without two consecutive numbers, with one check solver per condition. Each check has its own fragment and link; C2 runs only when C1 finds nothing.

X = C1.solve(assume G1(M)) if X: reject M with G1.clause(M, X) else: Y = C2.solve(assume G2(M)) if Y: reject M with G2.clause(M, Y)

Refinements written in ASP

The check can state the refinement itself with atoms clause(Id, T, Value): the atoms with one Id form one clause, true adds the literal T, false adds not T. T must be an interface atom. The loop reads them with G.clauses(X).

clause(1, pick(X), false) :- sum(X,Y). clause(1, pick(Y), false) :- sum(X,Y). clause(1, pick(X+Y), false) :- sum(X,Y).

Unsat cores, when the check looks for a witness

Sometimes the check confirms a candidate instead of refuting it: here, a graph is a solution when it can be 3-coloured. A candidate is rejected when the check is unsatisfiable, and G.core(C) builds the clause from the unsatisfiable core: the edges that together make a colouring impossible. 41 clauses suffice for 999 candidates. (In this example every satisfiable check counts as a counterexample in the statistics.)

if not C.solve(assume G(M)): reject M with G.core(C)

A refinement computed by its own solver

A third solver R computes the refinement from the candidate and the counterexample together. A solve call can take several assumption lists, here one per link.

X = C.solve(assume G(M)) if X: Y = R.solve(assume GA(M), GC(X)) reject M with GA.clause(M, Y)

Files from cegar.py

The Python prototype's files list the interface atoms in the glue directly (pick(X) :- num(X).). The keyword legacy on the link reads them that way. The Control tab imports such .lp files.

Raw Lua

The loop script is compiled to Lua (the Internals tab shows it, with ?internals=true). If the language lacks something, Edit as Lua in the Loop tab turns the script into Lua that you can change freely.

Mistakes in a script

The script is compiled while you type. Load any example above, open the Loop tab, and change C.solve into D.solve: after a moment the line is marked, the Loop tab label turns red, and the message says 'D' is not a declared solver. Other errors found before a run: unknown fragments, wrong indentation, reject outside on candidate, A.add inside the search of A. A run does not start while there are errors.

8. Your own problem

Start from the starter project (also New project in the Control tab). Its four fragments run as they are: the abstraction guesses a non-empty set of items, and the check looks for an item that is picked while a smaller one is not. With n = 4 it finds 4 solutions.

Replace the fragments step by step, running after each change:

  1. Put the domains in shared and the guess of a candidate in abstraction. Make the check #false. for a moment: it then never finds a counterexample, so the run lists all candidates. (An empty check is different: it has an answer set for every candidate, so every candidate has a counterexample.)
  2. List the atoms the check needs in glue, wrapped as glue(T).
  3. Write the check: rules that have an answer set exactly when the candidate is wrong. Add relevant(T) rules for the interface atoms each counterexample depends on.
  4. Compare with the Reference run on a small instance (lesson 5).

If a counterexample has no relevant atom, the run stops with relevant/1 derived nothing for link G, and the trace shows that candidate and counterexample. Your project is kept in this browser and comes back after a reload; download it (Control tab) to keep it for good.

Quick reference

Declarations

Statements

ScriptMeaning
x = eAssign a variable. Variables are local to the main script or to one on candidate block.
if a: ... elif b: ... else: ...Conditional. Only false and none are false.
loop:Repeat forever; leave with break or stop.
while e:Repeat while e is true.
repeat: ... until eRun the block, then stop once e is true.
for x in e:Run the block for each element of the list e.
break, continueLeave the innermost loop; go to its next round.
search A: / on candidate M: / blockRun A's own search; call the block for every candidate M. A candidate that is not rejected is a solution.
reject M with eAdd the clause (or list of clauses) e to the searching solver. Only inside on candidate.
accept MCount M as a solution (for models from solve; inside a search, not rejecting already accepts).
restartEnd the current search early; the next search starts afresh. Solutions found so far are not reported again.
stop "msg"End the run with outcome stopped (without a message: finished).
count n by eAdd e (default 1) to the custom counter n.
log a, bPrint a line to the messages in the Output tab.

A block may also follow the colon on the same line, if it is a single simple statement: if not M: stop.

Limits and gotchas

  • The time limit and the candidate limit (Loop tab, 0 = none) end a run with outcome limit. The default time limit is 60 s.
  • The seed matters only together with randomising options, such as options "--rand-freq=0.05". Without them, every seed gives the same search.
  • The no-progress guard stops Shapes 2 and 3 with the refinement made no progress when a refinement does not change the next candidate. Check that every head in a #program part(k). contains k.
  • An error inside clingo itself (not in the loop script) ends the run with "clingo stopped unexpectedly" and no message. The Output tab then shows the last lines clingo printed.
  • clingo's warnings and infos name the fragment and the line, and after the run they are marked in the editor: blue for an info, yellow for a warning.
  • Abort always works. Pause, Step, Stop and threads need a cross-origin isolated page; otherwise these controls are hidden or disabled.
  • All editors are read-only while a run is active.
  • ?fresh=1 starts from the default example instead of the project kept in this browser.
